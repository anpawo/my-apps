The best initial production approach is a deterministic provenance-first assignment with a constrained lexical and embedding fallback, plus explicit abstention. It should not be an invented clustering system and it should not share execution cwd with grouping by default.

Fleet should treat the reported cwd as a claim to validate, not as truth. The authoritative assignment should live in one place, in Fleet's session record, as a versioned field with source, confidence, timestamp, and the evidence used. VCX can propose updates, but Fleet should own acceptance. Execution cwd and grouping cwd should be separate fields. A session can run a command in a temporary directory, read a dependency elsewhere, or inspect an image without belonging to that project. Merging them invites exactly the reported failure where sessions land under slash.

The first tier is hard provenance: explicit user correction, explicit cd or project-open intent, Git ancestry, and a durable .fleet split marker. These should outrank inference. The second tier is evidence from the session's own recent actions, weighted by intent: shell directory changes and file edits are stronger than reads, and reads of incidental dependencies are weak. Reading a file is not membership. The third tier is retrieval over the known project catalogue, not unsupervised clustering, because the catalogue already supplies labels. For a small catalogue, BM25 over project paths, README style descriptions, and recent session artifacts, fused by reciprocal rank fusion with exact nearest neighbor search over fixed embeddings, is sufficient. Fixed embeddings avoid retraining and keep behavior stable. A small supervised classifier is premature without labeled data, and runtime LLM classification should be a bounded fallback for ambiguous cases, not the main path. The current ten second Haiku routing is too slow and too opaque to run per session.

Nested projects need longest-path matching with a boundary rule: a child project wins only when evidence is inside the child and not merely under the parent, and a parent project should not swallow a child because of an early read. Topic changes need session segmentation or a reassignment event, not silent rewriting of history. Ambiguity should abstain to an unassigned or review bucket rather than force a false assignment. Corrections must be stored as labels and should pin future decisions for that session.

OpenEvolve, ShinkaEvolve, and GEPA have different roles. OpenEvolve fits offline evolution of a deterministic scoring or ranking function when there is an evaluator and labeled targets, as documented at https://github.com/algorithmicsuperintelligence/openevolve. ShinkaEvolve fits adaptive program evolution, but its reported wins are on other tasks, per https://sakana.ai/shinka-evolve/ and https://github.com/SakanaAI/ShinkaEvolve. GEPA fits reflective optimization of prompts or configurations with Pareto selection, per https://arxiv.org/abs/2507.19457 and https://github.com/gepa-ai/gepa. None of them should be used to invent project labels from unlabeled sessions. The right offline strategy is to use OpenEvolve or GEPA only after a labeled evaluation set exists, to tune weights, thresholds, abstention, and fusion parameters for a fixed architecture. AlphaEvolve's evaluator loop, described at https://arxiv.org/abs/2506.13131, is a useful pattern, but its results do not transfer to Fleet grouping.

The evaluation contract must come first. Ground truth should be human verified assignments at decision time, not later corrected directories. Splits should be by session and by project, with no future information leaking into the decision. Metrics must report false assignments separately from abstentions, plus routing coverage, p50 and p95 latency, memory, stability under repeated runs, and end to end behavior when a session is reassigned. Accuracy without coverage is misleading, because abstention can hide failure.

What remains unproven is whether lexical plus embedding retrieval beats deterministic provenance alone on real ambiguous sessions, and what abstention threshold preserves usefulness. The concrete falsifier is a labeled evaluation where the proposed hybrid produces more false assignments than provenance-only assignment at equal or better coverage, or where corrections do not reduce repeat errors. If that happens, the retrieval tier should be removed or narrowed, not tuned harder.
