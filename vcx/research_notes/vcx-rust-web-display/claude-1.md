# Claude leg 1: VCX to Rust with a web display

Written 25/11/2026. Every source below was read on 25/11/2026 unless another date is given. "Estimate" marks a figure I did not measure or read. I ran one headless measurement for this answer (described in "Measurements made for this answer"); it ran Playwright's own WebKit build, not the system WebKit, opened no window and built nothing.

## Recommendation in 5 lines

1. Display: one system WKWebView per window, holding the whole window content (transcript, composer, cards, task bar), loaded from a hot-reloaded template folder, with a virtualized transcript: 5,000 rows cost about 49 MB in a WebKit content process virtualized against 231 to 316 MB as a full DOM (measured, below).
2. Order: put the web display into today's Swift app first (it brings the hot reload and removes the SwiftUI bugs on its own), then port the runtime workers to Rust behind the same socket protocol, then the frontend core, and only then swap the Swift shell for wry + tao (not full Tauri, not Dioxus, Blitz or GPUI): every serious option runs the same WKWebView, so the shell language barely moves RAM.
3. Processes: keep the frontend/worker split and live update; one WebKit content process per window by default (an agent's runaway chart then freezes one window, not all); windows opened as "related" views through `window.open` share one process (measured: 8 windows in 194 MB instead of about 400 MB), an option to take once a hang watchdog exists.
4. The template is trusted code that goes live only after an offscreen test render passes, with a last-good copy and a built-in template compiled into the binary as fallbacks; agent chart HTML runs in sandboxed `srcdoc` iframes that reach the app only through an allowlisted, rate-limited `vcx.live`.
5. Expect RAM about equal to today at best, not lower (estimate for 8 windows: 300 to 400 MB with shared processes, 490 MB or more with one per window, against 253 MB for 7 today), about 11 to 16 developer-weeks with agents (estimate); stop if the step-0 spike on a real long thread exceeds 600 MB for 8 windows or drops frames while streaming.

## Measurements made for this answer

Scripts: `/tmp/vcx-claude1-probe/measure.mjs`, `measure2.mjs`, `measure3.mjs` (scratch, outside the repo). Engine: Playwright WebKit build 2368 (from `~/Library/Caches/ms-playwright`), headless, viewport 900x1000. Synthetic transcript: 5,000 rows alternating a one-line user prompt and an agent answer (heading, two paragraphs with a link and inline code, a folded `<details>` of 12 tool lines, a 10-line code block, a small table every tenth answer): 72,006 DOM elements as a full DOM. Memory is `footprint -p` of the new `WebContent` processes. Frame times are headless `requestAnimationFrame` deltas; headless WebKit has no real display link, so those timings are indicative only and I do not base any decision on them.

| Case | WebContent processes | Footprint per process | Note |
|---|---|---|---|
| Blank page | 1 | 12 MB | baseline cost of one content process |
| 5,000 rows, full DOM | 1 | 316 to 318 MB | two runs |
| 5,000 rows, full DOM + `content-visibility: auto` | 1 | 230 to 231 MB | still 72,006 elements; headless scroll got worse, not better |
| 5,000 rows, virtualized (about 220 elements in the DOM) | 1 | 49 MB | row HTML kept as JS strings, naive innerHTML window |
| 8 pages, virtualized, separate pages | 8 | 50 MB each, 400 MB total | one process per page |
| 1 page + 7 `window.open` popups, virtualized | 1 | 194 MB total | related pages share one process |

Other live readings on this Mac (25/11/2026 15:22, `footprint` and `ps`): One Text's WebKit helpers were WebContent 523 MB footprint (92 to 109 MB RSS), GPU 33 MB, Networking 7 MB. A blank page costs 12 MB, so One Text's 315 to 523 MB is its page content and JS heap, not a fixed WebKit tax: the 19/11 conclusion "a webview brings about 400 MB" mixes the engine's cost with One Text's content. At that moment no WebKit helper process was attributed to VCX (responsible-process lookup over all `com.apple.WebKit.*` processes): with no chart on screen, today's VCX pays nothing for WebKit.

## 1. Stack

The question splits in two: which engine draws the chat, and which language runs the shell and the core. For an HTML/CSS/JS template that agents restyle live and for free-form agent charts, the engine has to run JavaScript, which on macOS without Electron means the system WebKit. Tauri, wry, a Swift shell and Dioxus desktop all draw through that same WKWebView, so their display RAM, scrolling, IME, accessibility and text selection are the same; they differ in the app process (tens of MB) and in how much of the WKWebView API they expose.

Tauri 2 (2.12.7, crates.io, updated 18/11/2026; https://crates.io/api/v1/crates/tauri). Mature, documented, with streaming `Channel`s that "are designed to be fast and deliver ordered data", while its event system "is not designed for low latency or high throughput situations" (https://v2.tauri.app/develop/calling-frontend/). Its capability files gate which commands each window may call, but registered commands are open to every window by default (https://v2.tauri.app/security/capabilities/). Headless test: "macOS has no WKWebView driver tool available"; `tauri-driver` covers Windows and Linux only, and the WebdriverIO Tauri service ships an embedded WebDriver server for macOS (https://v2.tauri.app/develop/tests/webdriver/). RAM: same WebKit as below, plus its app process (One Text's was 76 MB, brief, 19/11). Most of what Tauri adds (bundler, updater, JS plugin API, ACL files, npm frontend tooling) duplicates what VCX already has (its installer, live update, signing) or is not needed; it also puts one more layer between VCX and WKWebView options it needs.

wry + tao without Tauri (wry 0.58.0 updated 25/11/2026, tao 0.38.0 updated 24/11/2026; crates.io). What I checked in the wry 0.58.0 source: `WebViewBuilderExtMacos::with_webview_configuration` takes a raw `WKWebViewConfiguration` (lib.rs:1667), `WebViewExtMacOS::webview()` returns the WKWebView handle (lib.rs:2518), a `with_new_window_req_handler` returns `NewWindowResponse::Create`, which on macOS needs the caller's configuration (https://docs.rs/wry/latest/wry/enum.NewWindowResponse.html), there is a web-content-process-terminate handler (lib.rs:1660), and custom protocols (`with_asynchronous_custom_protocol`, https://docs.rs/wry/latest/wry/struct.WebViewBuilder.html). So everything VCX needs (a `vcx://` scheme handler for the template, related views, `takeSnapshot` through objc2, crash recovery) is reachable. One trap: wry's script-message delegate passes the sending frame's request URL to the IPC handler but not `isMainFrame` nor the security origin (wkwebview/class/wry_web_view_delegate.rs:49), and the `ipc` handler is visible to every frame, so the Rust side must reject any message whose URL is not the template's own `vcx://` URL (a `srcdoc` iframe reports `about:srcdoc`). This is my pick for the final shell.

A Swift shell around WKWebView (today's app, with SwiftUI transcript code replaced by one web view per window). Full WKWebView API with no wrapper (`WKScriptMessage.frameInfo.isMainFrame`, `WKContentWorld`, `callAsyncJavaScript`, `WKURLSchemeHandler`, `createWebViewWith` for related views), and the offscreen snapshot path already works in VCX's checks (`view.takeSnapshot` in Check.swift:2483 and ChartInteractionCheck.swift:213). Same WebKit RAM. It is the cheapest place to build and prove the display, and a sound long-term answer if the Rust move stops at the workers.

Dioxus desktop (dioxus 0.7.10, crates.io, 16/10/2026). Same WKWebView through wry, but the UI is Rust (`rsx!`) diffed in Rust and patched into the DOM; its hot reload of RSX, assets and Rust is a `dx serve` development feature (https://dioxuslabs.com/learn/0.7/essentials/ui/hotreload/), not a runtime template an agent edits in a shipped app. It works against wish 2.

Dioxus Native / Blitz (blitz-dom 0.2.4, crates.io, 24/11/2026). "Blitz is currently in a beta state... usable for making apps if you are an early adopter... still many bugs and missing features"; no JavaScript; accessibility through AccessKit (README, https://github.com/DioxusLabs/blitz). No JS means no free-form charts and no hot-reloaded behaviour (only CSS), and text selection, IME and long-list virtualization would be VCX's problem on a beta engine. RAM unmeasured; likely lower than WebKit (estimate: one process, 60 to 150 MB). Not for a tool used all day, in late 2026.

GPUI (gpui 0.2.2, crates.io, 30/10/2026). Fastest rendering of the set (it is Zed's), but "still pre-1.0. There will often be breaking changes", and on macOS its README asks to install Xcode for Metal (https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md), which VCX avoids. The display would be Rust code, so no hot-reloaded template, and free-form charts would still need a WKWebView. Good headless story (`#[gpui::test]`, `TestAppContext`, same README).

Others. Slint (1.19.1, 24/11/2026) can load `.slint` markup at runtime through its interpreter, the only non-web kit with a real reloadable UI file, but it is not HTML/CSS, has no JS, and its text and Markdown story is weaker than WebKit's (estimate). iced (0.14.0, 07/12/2025) and egui (0.37.0) are immediate or Elm-style kits with no reloadable template and immature IME and accessibility on macOS (estimate). Sciter and Ultralight stay out: closed source, unmeasured, and a second JS engine to trust. Servo embedding is not production-ready on macOS (estimate).

Per-feature notes for the WebKit options (all four): IME is Safari's own in a `<textarea>` or `contenteditable`; key handlers must skip events while `KeyboardEvent.isComposing` is true (https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/isComposing) so Enter that confirms a Japanese or Chinese candidate does not send the prompt. VoiceOver reads the DOM natively if the template uses real elements and ARIA roles (`log` for the transcript, `dialog` for question cards). Text selection is native, with one catch from virtualization (section 3). Keyboard focus: putting the composer inside the same web view removes the native-versus-web focus fight behind today's "focus theft". The find bar can use the CSS Custom Highlight API, Baseline 2025 (https://developer.mozilla.org/en-US/docs/Web/API/CSS_Custom_Highlight_API), but its search must run in the core over the model because a virtualized DOM does not hold every row.

## 2. Windows and processes

Keep one window per session: Fleet, the task bar, `vcx --send` and the owner's habits are all per window; a single tabbed window would change how he works for a saving that related views give anyway.

How WebKit shares processes. `WKProcessPool` is deprecated since macOS 12: "Creating and using multiple instances of WKProcessPool no longer has any effect" (https://developer.apple.com/tutorials/data/documentation/webkit/wkprocesspool.json). Apple's documented rule is "Each web view is given its own Web Content process until an implementation-defined process limit is reached" (quoted by Apple DTS in https://developer.apple.com/forums/thread/107502). The private `_relatedWebView` was deprecated in 2024 as incompatible with site isolation (webkit-changes commit 96178a, August 2024; the list page answered 403 to my fetch, so this rests on the search result's title). The public way to share is a related view: a page that calls `window.open` and an app that answers `WKUIDelegate.webView(_:createWebViewWith:for:windowFeatures:)` (or wry's `NewWindowResponse::Create`) with the configuration WebKit hands it. My measurement: 1 opener + 7 popups ran in one content process, 194 MB for 8 virtualized 5,000-row transcripts, against 8 processes and 400 MB as separate pages. A GPU process (about 33 MB) and a Networking process (about 7 MB) are shared by the whole app either way (One Text readings above).

The price of sharing: one content process has one JS main thread. A chart whose script loops, or a heavy re-render in one window, freezes every window's display (agents keep running, they live in workers). Cross-site iframes do not get their own process unless WebKit's site isolation is on, and I found no source that it ships enabled in Safari 26 (https://docs.webkit.org/Deep%20Dive/SiteIsolation.html describes it as tested behind a flag). So: start with one process per window (about 50 MB each virtualized, estimate 60 to 100 MB on real threads with images and highlighted code), and switch to related views only after a watchdog exists (the core pings each page once a second; two missed pings reload that window with free-form charts frozen to their last snapshot).

Today's VCX creates a fresh `WKWebViewConfiguration` per chart block (Chart.swift:403), so each chart or table block on screen gets its own content process under Apple's rule above. One web view per window with charts as iframes caps the process count at one per window, a saving on chart-heavy threads.

Frontend/worker split: keep it as is. Workers (11 to 22 MB each) own the agent CLIs, survive frontend swaps, and their socket RPC is the natural seam for the Rust port: a Rust worker speaking the same protocol can be swapped in under the Swift frontend one provider at a time. Live update gets cheaper: a template change no longer needs a frontend swap; a binary update still uses the existing mechanism, and the new frontend restores each window from core state (section 4).

## 3. Rendering and streaming design

Ownership. The core (Swift first, Rust later) owns the transcript model: rows with stable ids, a kind, a version, and for agent text a list of Markdown blocks. The page is a pure view of that model plus local UI state it reports back (scroll anchor, folds, composer draft). That single rule is what makes reloads, live updates and tests cheap.

Markdown in the core, styling in the template. Parse in the core (Rust: pulldown-cmark 0.13.6 or comrak 1.2.0, both on crates.io, updated 30/10 and 23/11/2026), sanitize there (no raw HTML from agent text reaches the DOM), and send per block a small typed tree or a sanitized HTML fragment with semantic classes. CSS restyles everything; the template may register a JS renderer for a block kind (`code`, `table`, `chart`, `question`) to change structure. Streaming parse: only the last open block (paragraph, list, fence) is re-parsed per batch; closed blocks are frozen and never resent. Syntax highlighting in the core too (estimate: cheaper than shipping a JS highlighter into every window's heap).

Transport. Core to page: batched patches `{row, block, op, payload}` coalesced to at most one batch per display frame, delivered with `callAsyncJavaScript` (Swift) or `evaluate_script` (wry), or pulled: the page posts `pull` from its `requestAnimationFrame` when notified dirty, so a hidden or occluded window (WebKit throttles its frames) accumulates nothing in JS and gets one compact snapshot when it shows again. Page to core: one handler, a closed set of verbs (section 4). Do not use per-token messages or Tauri's event system for tokens (its own docs say so, section 1).

Long transcripts. Virtualize: the DOM holds the visible rows plus one or two screens of overscan; heights are cached per row id and width; positions are anchored to a row (id + offset) so heights changing above the viewport never move what he reads; "stick to bottom" while streaming unless he scrolled up. Recycle row elements by kind instead of `innerHTML` rebuilds. Measured above: 49 MB against 316 MB for 5,000 rows; `content-visibility: auto` alone kept every element and saved only about 85 MB. Two virtualization costs to design for: a selection that spans rows must keep those rows mounted while it exists (and ⌘C over a long range is served by the core from the model), and the find bar searches the model and scrolls a row into view before highlighting.

Animations (wish 3). The template owns them: CSS transitions or the Web Animations API, 200 to 350 ms ease-out or spring curves; growing content is revealed by animating the container's height from its measured old size to its new one (FLIP), batched with the streaming frame so rows never jump; `@media (prefers-reduced-motion: reduce)` maps to macOS Reduce Motion and turns every one into a short opacity fade. Nothing animates on a timer at rest, so idle CPU stays near zero.

Charts. Two tiers. The data-only spec from the 19/11 council (`{v, kind, data, x, y, title}`) and `vcx.chart(...)` are drawn by the trusted template itself, inline, cheap, with lightweight-charts bundled in the template folder instead of a CDN (works offline, and no remote code runs in the trusted page). Free-form agent HTML goes in an `<iframe sandbox="allow-scripts" srcdoc=...>` without `allow-same-origin`: opaque origin, no access to the parent DOM or to `webkit.messageHandlers` (the handler must still reject any message whose frame is not the main frame, section 1). It talks to the template only with `postMessage`: `size` and `live`. Pinned and expanded blocks become the same iframe moved to another layer of the same page, which removes today's wheel-capture and pinned-height bugs that come from nesting native web views in a SwiftUI scroll view.

Headless detail from today's code: "A window that is not on screen runs no ResizeObserver" (Chart.swift, Coordinator comment), and frames are throttled likewise, so the template must also expose a synchronous `flush()` that applies pending patches and lays out without waiting for a frame; offscreen checks call it before `takeSnapshot`.

## 4. The hot-reload template

Layout. A folder outside the binary, for example `~/Library/Application Support/VCX/template/` (or `vcx/template/` in the repo, symlinked, so changes have git history), holding `manifest.json` (`{"contract": 3, "version": "...", "entry": "index.html"}`), `index.html`, `style.css`, `app.js`, `renderers/*.js`, `vendor/lightweight-charts.js`. Served to the page through a `vcx://template/` scheme handler that reads only the active copy (below), never the working folder directly.

Data contract. A versioned, written schema (JSON Schema checked into the repo) of: core to page (`snapshot`, `patch`, `ui` for status and task bar, `question`, `theme`, `restore`) and page to core (`ready{contract}`, `pull`, `send{text, attachments}`, `answer{question, option}`, `command{name, args}` for the palette's known commands, `openFile{path}`, `state{anchor, selection, composer, folds}`, `chart.live{url, seconds}`). The core refuses a template whose `contract` major differs from its own and keeps the previous one.

Applying an edit. FSEvents on the working folder, debounced about 300 ms, then a test render before anything goes live: copy the folder to a staging directory, load it in an offscreen web view with a fixed fixture transcript (a few hundred real-shaped rows: Markdown, tables, a tool fold, a question card, a data chart, a free-form chart), call `flush()`, and require: `ready` within 2 s with a matching contract, no `window.onerror` or unhandled rejection, every fixture row with a non-zero height, the composer element (`[data-vcx=composer]`) present and focusable, and a snapshot that is not blank. Pass: the staging copy becomes `active/` (the previous one kept as `last-good/`, plus a few dated copies) and every window reloads. Fail: windows stay on the current copy, the status bar shows the first error, and the full report goes to a file the agent can read (`template-errors.log`), so an agent that edits the template gets its own feedback loop.

Reloading without losing state. CSS-only changes swap the `<link>` in place: no reload, nothing lost. A JS or HTML change: the core already holds the transcript and the composer draft (the page mirrors draft text, chips and caret to the core on each input, debounced), asks each page for `state` (anchor row id + pixel offset, selection as row/offset pairs, folds, find query), reloads, then sends `snapshot` and `restore`. A 150 ms cross-fade (a snapshot image over the view during the reload) hides the blank frame. A window mid-question keeps its question card because the question is core state.

Fallbacks. Three levels: `active/`, then `last-good/` if `active/` fails `ready` twice at runtime, then a template compiled into the binary, also reachable by a menu item and a key chord ("Safe display"), so a broken template can never leave him without his main tool. A WebContent crash (wry has a terminate handler, WebKit's delegate has `webViewWebContentProcessDidTerminate`) reloads the window from core state; two crashes in a minute switch that window to the built-in template.

Agents editing it. Agents edit the working folder only; the test render is the gate; history lives in git. Everything an agent writes into the template is trusted code once applied (it runs with the bridge), so it is reviewed like source: the staging diff is shown in the status bar line with a one-key revert.

Security. The template can only call the verbs above; no verb runs a shell command, writes a file, or reaches a worker except `send` (which is what typing in the composer does) and `command` restricted to the palette's own list. `openFile` opens with the default app through `NSWorkspace` after resolving the path, never executes (refuse `.app`, `.command`, `.sh`, `.terminal` and executables). Message handlers accept only main-frame messages whose URL starts with `vcx://template/` (in wry: check the request URI, since it gives no `isMainFrame`). A Content-Security-Policy on the template (`default-src vcx:; script-src vcx:; connect-src 'none'; frame-src about: blob:`) keeps the page from loading remote code. Chart iframes get no handler. `vcx.live` today accepts any `http` or `https` URL (Chart.swift, `live(_:in:)`), including `localhost` and private addresses, and an agent-written page can display what it reads and leak it through an image URL; in the new design the core should refuse loopback, link-local and private ranges unless allowlisted, cap the rate (5 s minimum already exists) and the number of feeds per window.

## 5. Migration path

Step 0, spike (about 3 to 5 days, estimate). In the current Swift app, behind a setting, one window's transcript drawn by a WKWebView from a template folder, fed from the existing model, virtualized. Measure on the owner's longest real archived thread, with 1 and 8 windows: total footprint of VCX plus every WebKit helper attributed to it (the responsible-process method above), scroll and streaming frame pacing on screen on another desktop (not his), and typing latency in the composer. Stop or redesign if 8 windows exceed about 600 MB total, or streaming into a 5,000-row thread misses more frames than today's SwiftUI view on the same thread, or IME and VoiceOver fail basic checks.

Step 1, the transcript is web (2 to 3 weeks, estimate). Template folder, contract v1, hot reload with the test-render gate and fallbacks, Markdown in the core, charts as iframes, offscreen render checks ported (section 6). Usable on its own: every look tweak is a file edit. Measure: frontend + WebKit footprint against 253 MB / 7 windows; template reload time.

Step 2, the whole window is web (2 to 3 weeks, estimate). Composer with chips, palette, question cards, find, task bar, status bar into the template; the SwiftUI view tree goes away except the window shell and menus. Measure: focus and IME checks, key latency, frontend process footprint (should fall when SwiftUI and CoreText measuring leave, estimate).

Step 3, Rust workers (3 to 4 weeks, estimate). Port the runtime worker (CLI drivers for `claude -p` stream-json, `codex app-server`, Ollama, the headless-browser debates) to a Rust binary speaking the existing socket protocol; the Swift frontend talks to either worker. One provider at a time, live-swapped like today. Measure: worker footprint (11 to 22 MB today), recovery and swap checks passing against the Rust worker.

Step 4, Rust frontend core and wry/tao shell (3 to 5 weeks, estimate). Session store, archive, Fleet presence, Markdown and the template server in Rust; the shell becomes tao windows + wry web views, menus through `muda`, the menu bar item through `tray-icon`, global hotkeys through `global-hotkey` (all tauri-apps crates, versions not checked today). Make the switch only if step 3 went well and the Rust core is the code he wants to grow; otherwise the Swift shell calling the Rust core over the same socket is a fine end state.

What to keep in Swift: nothing is forced to stay. TCC grants follow the signed bundle identity and the certificate requirement (his ERRORS notes on ad-hoc signatures apply equally to a Rust binary), so keep the same bundle id and certificate. `codesign` comes with the Command Line Tools and cargo needs no Xcode (GPUI would, which is one more reason to skip it). The offscreen interaction checks that route real NSEvents into unshown windows rely on AppKit; under wry they need objc2 calls into the same APIs, about a week of port (estimate).

## 6. Risks and costs

RAM. The web display does not save RAM against today's 253 MB for 7 windows. Estimate for 8 windows: separate processes 8 x 50 to 100 MB + GPU 33 + Networking 7 + app process 50 to 100 = about 490 to 940 MB on real threads (the low end is my synthetic measurement); with related views about 194 MB + 40 + app = 300 to 400 MB. Without virtualization, about 2 GB. Virtualization is not optional.

Energy and CPU. Near zero at rest if the template runs no timers or rAF loops while idle; chart pages with `vcx.live` poll as today. WebKit throttles occluded windows, which also pauses background live charts (acceptable). Estimate, not measured.

Input latency. Typing in a WebKit `<textarea>` is native-speed; the IPC hop is only on send. Risk: a template that does heavy work on `input` events; the test render can time a synthetic burst of 200 key events and fail above a budget.

IME and accessibility. Better than the current custom `NSTextView` path for IME (Safari's), equal or better for VoiceOver if the template uses semantic elements. Regressions come from custom key handlers (check `isComposing`) and from virtualization (screen readers see only mounted rows; mark the list as `role="log"` with `aria-setsize` and `aria-posinset`).

Rewrite size. About 11 to 16 developer-weeks with agents for steps 0 to 4 (estimate). Steps 0 to 2 (about 5 to 7 weeks) give every visible benefit; steps 3 and 4 are the language change.

Keeping the 7,500 lines of checks. Sort them by seam. Runtime, RPC, recovery, swap, archive and bounds checks talk to workers through the socket: keep them in Swift as a black-box conformance suite and run them against the Rust worker unchanged in step 3; port them to Rust tests only once Rust is the only implementation. Provider checks become record/replay fixtures (JSONL captured from real CLIs) shared by both implementations. UI checks split into fast template tests in headless WebKit (Playwright WebKit as used here, no window, seconds per run) against the fixture transcript, and a smaller set of in-app offscreen `takeSnapshot` renders through the real shell, with `--render` and `--render-demo` kept as the README GIF path.

Other risks. WebKit's process model changes under him (site isolation, process limits): measure footprint on each macOS update. wry's API moves (0.x, about one minor per month): pin versions. Agents breaking the template: mitigated by the gate, last-good and built-in fallbacks.
