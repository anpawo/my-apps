**Recommendation Summary (5 lines)**
The optimal path shifts to **Tauri 2 with system WebKit**, but our process-sharing RAM estimates were overly optimistic; we must budget for distinct WebContent processes per window (~400–900 MB total) rather than a single pooled context. We will implement **automatic hot-reloading** using Rust's `notify` crate and a "last-good" JSON state fallback to protect against user edits breaking the UI, removing the manual approval step. For live charts, we will use **Rust-brokered polling** for opaque-origin iframes since direct CORS-free fetching is impossible in sandboxed environments. The migration proceeds in three phases: isolate the chat transcript in a WebView (Swift host), port the core logic and workers to Rust, then swap the entire app shell to Tauri, accepting an effort estimate of 10–14 weeks.

### 1. Stack Comparison and Recommendation
**Tauri 2 (Rust + system WebKit)** remains the recommendation, but the justification requires adjustment regarding maturity and ecosystem tools. While **wry/tao** offers a leaner raw bridge, Tauri's `tauri-plugin-fs` provides essential file-watching capabilities for hot-reloading that would require significant custom Rust boilerplate to implement in wry. Regarding **Dioxus Native**, while its RAM potential is lowest, the maturity risk remains high on macOS 26 ("Tahoe"), and rendering complex agent-generated charts without a JS engine or Canvas fallback is a significant bottleneck. The recommendation stands for Tauri as the pragmatic balance between native performance (Rust) and web flexibility (WebKit), but we must lower expectations for "zero overhead" claims regarding process sharing.

### 2. Windows and Processes Architecture
**Strategy Shift: Pooled Data Stores, Distinct WebContent Processes.**
Our previous assumption of a single shared WebContext across windows was partially incorrect based on source code evidence (`WebProcessPool.cpp` logic). While Tauri can configure a **shared `WKWebsiteDataStore`**, Apple's implementation does not guarantee that unrelated windows sharing that store will share the same `WebContent` process; typically, each window spawns its own helper until specific "related view" conditions (like popups from the same origin triggered by JS) are met. Therefore, we should architect for **N WebContent processes** (one per window) but optimize by ensuring windows share the same data store and origin to maximize potential caching. For 8 windows, this pushes RAM estimates to **400–900 MB**, not the aggressive 350 MB predicted earlier. The architecture will still use a single Rust backend process, but we must accept higher GPU/memory overhead for the multiple WebKit helper processes as the price of stability and isolation.

### 3. Rendering and Streaming Design
**Token Flow & Virtualization:** This section remains largely **unchanged**. Using JS libraries like `react-window` or `jsdom-virtual` to render only visible DOM nodes (e.g., 100 rows) while streaming tokens via the IPC bridge is still the correct approach for managing memory in a WebView-based solution. The strategy of buffering chunks in Rust and injecting them into a virtualized DOM list holds true for mitigating frame drops during long transcript generation. The choice to render Markdown in JS (`marked.js`) rather than sanitizing everything in Rust allows for better fidelity with agent-generated HTML structures, provided the DOM virtualization handles the node count efficiently.

### 4. Hot-Reload Template Implementation
**Strategy Shift: Automatic Reload vs. Manual Approval.**
We **yielded** on Point 10 regarding who applies template edits. The previous "owner approval" flow is too slow for a developer tool; the new strategy is **automatic injection**. We will use Rust's `notify` crate (via `tauri-plugin-fs`) to watch the asset directory. Upon detecting a change, Rust sends an IPC message to the WebView JavaScript thread to swap modules or reload the view. Crucially, we retain the **"last-good" safety mechanism**: before injecting new code, the JS runtime saves the current DOM state or checks a version hash; if the user manually edits `index.html`, the app boots in "Safe Mode" using a cached good version or displays a warning, allowing a clean restart to revert. This balances speed with the need for robustness against user errors.

### 5. Migration Path (Shippable Steps)
**Phase Sequence: Hybrid Shell -> Rust Core -> Full Tauri.**
The high-level order remains **unchanged**, but the specific implementation details of Phase 1 shift slightly due to new insights.
*   **Phase 1:** Embed a WebView into the existing Swift host to handle transcript rendering, verifying that virtualization works in this constrained environment before committing to a full rewrite.
*   **Phase 2:** Replace Swift UI controllers with a Rust backend (Tauri core) while keeping the WebView shell; port Agent Workers to Rust for better IPC control.
*   **Phase 3:** Migrate the entire application logic to Tauri v2, implementing the multi-process WebKit architecture and integrating the `headless-ui-test` suite.
We **yielded** slightly on the "stop conditions" regarding RAM; instead of stopping immediately at 600 MB (as we might have planned for a single context), we now set the stop threshold higher (e.g., >1 GB) or accept the ~800 MB footprint as the baseline trade-off for a stable, multi-window WebView experience on macOS.

### 6. Risks and Costs
**RAM & Stability: The Process Tax.**
*   *Risk Confirmation:* WebKit is indeed heavier than native CoreText, but the bigger risk now confirmed is the **process tax**. Unlike our optimistic estimate of 350 MB for 8 windows, we must budget **~400–900 MB** depending on sharing behavior. This is still likely better than a naive SwiftUI implementation with 8 independent ViewModels, but it is not "tiny."
*   *Mitigation:* We will implement aggressive memory monitoring at runtime. If the app exceeds 1 GB, we can programmatically unload old chat history rows to bring the DOM count down, as the heavy lifting in RAM is both the WebContent processes and the visible DOM nodes.
*   *Rewrite Effort:* With the addition of the custom process-management logic and potential debugging of `headless-ui-test` compatibility (if available via workarounds), we estimate **10–14 weeks** for a single senior developer, slightly higher than the 8–12 week initial guess to account for the learning curve on Tauri's specific macOS quirks.
*   *Tooling Risk:* Since `headless-ui-test` crate returns a 404 on crates.io, we cannot immediately rely on it. We may need to fork or build our own headless driver using `wry` and WebDriverIO services in Rust, adding 1–2 weeks of initial setup time before the 7,500-line verification suite can be fully ported and validated.
