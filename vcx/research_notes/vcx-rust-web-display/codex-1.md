Use a Rust core with a thin AppKit host and one system WKWebView per session window.  
Ship the disk-backed transcript inside today's Swift VCX first, with the native composer still in charge of input.  
Keep the session workers and their live-update handover, then port worker internals behind the same protocol.  
Render structured charts through app-owned components and preserve free-form charts in isolated, on-demand frames.  
Make the eight-window replay the release gate for RAM, scrolling, input, and energy, with the current VCX as the control.

## 1. Stack

I would keep the existing AppKit host through the first release and let it remain thin Swift if it preserves macOS behavior with less code. Rust owns the transcript model, parsing, persistence, and eventually the workers. Use plain HTML, CSS, and JS with a small versioned adapter. If an all-Rust host becomes valuable, compare direct AppKit/WebKit bindings with wry/tao using the same bundle and replay. The former exposes native WebKit delegates directly, while wry/tao provides Rust windowing and webview plumbing. Tauri 2 would be my packaged alternative if its bundler and IPC reduce maintenance enough to justify migrating the shell. These choices all use the same system webview on this Mac, so I would expect the display implementation and compositor workload to dominate the performance differences. [Apple WKWebView](https://developer.apple.com/documentation/webkit/wkwebview), [Rust WKWebView bindings](https://docs.rs/objc2-web-kit/latest/objc2_web_kit/struct.WKWebView.html), [wry](https://github.com/tauri-apps/wry/blob/dev/README.md), [tao](https://github.com/tauri-apps/tao), [Tauri webview versions](https://v2.tauri.app/reference/webview-versions/) (read 2026-11-25).

For the WKWebView options, let the browser handle selectable transcript text and semantic HTML. Keep AppKit responsible for the responder chain and start with its existing composer for marked text, candidate placement, and edit commands. Test VoiceOver and keyboard traversal where the native and web content meet. Use Playwright headless WebKit for fast DOM, animation, and screenshot checks, then an unshown AppKit window with the shipped system WKWebView for snapshots and actual native event routing. Playwright ships its own WebKit build. Tauri's current docs describe a macOS embedded WebDriver through WebdriverIO and a separate commercial driver. The embedded driver still needs its windowless behavior demonstrated in VCX, and DOM automation leaves native IME and responder routing unverified. [WebKit input and accessibility changes](https://webkit.org/blog/15443/news-from-wwdc24-webkit-in-safari-18-beta/), [WebKit responder issue](https://bugs.webkit.org/show_bug.cgi?id=249976), [WKWebView snapshot binding](https://docs.rs/objc2-web-kit/latest/objc2_web_kit/struct.WKWebView.html), [Playwright browsers](https://playwright.dev/docs/browsers), [Tauri WebDriver](https://v2.tauri.app/develop/tests/webdriver/) (read 2026-11-25).

Dioxus Desktop runs a Rust virtual DOM over wry/tao. I would use it if Rust-defined views were the priority. A disk-edited JS display with independent releases fits a smaller adapter. Native/Blitz is a different renderer, with AccessKit and native event handling, and the Dioxus previews still use a beta Blitz dependency. GPUI is a credible native renderer with Zed's test contexts, list virtualization examples, and a macOS headless Metal benchmark. Both native routes would need new selectable transcript components and a separate execution surface for the existing interactive JavaScript charts. Servo is a credible independent engine for a follow-up spike, with embedding APIs, macOS builds, and headless screenshots. Its current releases show active work on the accessibility and input paths, so I would budget for integration and require the same chart and input tests. ## 2. Windows and processes

Use one app frontend, eight native windows when eight sessions are open, and one transcript view per window. One app PID is compatible with several WebContent PIDs. A single WKWebView can present eight logical sessions through tabs with one live page, or move between windows, but it can display only one of those windows at a time. Tabs are an optional lower-memory workspace mode. Start by pausing offscreen work. If RAM demands it, consider evicting views of minimized or deliberately parked windows after saving their state, and measure their wake latency before enabling eviction by default. [Apple WKWebView](https://developer.apple.com/documentation/webkit/wkwebview), [WebKit on inactive-page power](https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/) (read 2026-11-25).

Budget for an independent WebContent process per live page. The WebKit header describes per-view processes up to an implementation-defined limit, and marks creating multiple `WKProcessPool` instances as having no effect. Related views are a relationship WebKit can use, including when it supplies a configuration for a newly opened web window. The explicit Cocoa related-view setter is in the private category. A common origin, data store, or pool gives VCX no public guarantee that eight top-level views will share a renderer. WebKit can also split cross-site frames when site isolation applies. Record actual PIDs and per-PID footprint from the signed build on the installed Tahoe version, including GPU and networking helpers, after chart activation, after repeated navigation, and after closing windows. Treat any sharing observed as a measured benefit for that build. [WebKit process-pool header](https://github.com/WebKit/webkit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKProcessPool.h), [WebKit related-view implementation](https://github.com/WebKit/webkit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebViewConfiguration.mm), [WebKit site isolation](https://docs.webkit.org/Deep%20Dive/SiteIsolation.html) (read 2026-11-25).

Keep the workers as the owners of agent processes and the Swift frontend's replacement independent of them, as described in the supplied VCX brief (read 2026-11-25). Negotiate protocol versions before any handover. Preflight all restore entries, transfer each lease through the existing coordinator, and resume from a sequence cursor. Until the replacement acknowledges readiness, the existing frontend stays usable. If leases have begun moving and the transfer fails, explicitly roll them back. Test a worker surviving both frontend death and web-content death mid-turn, with drafts and user edits surviving the handover. Template reloads use the same attached frontend, so the owner can apply them mid-turn without a worker swap. WKWebView exposes a content-process termination callback for rebuilding its page. [Apple termination callback](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webviewwebcontentprocessdidterminate%28_%3A%29) (read 2026-11-25).

## 3. Rendering and streaming

Have Rust reduce provider events to versioned snapshots and ordered patches, keyed by session, row, stream generation, and sequence. Give each window a bounded queue. Batch text from the same row on a short timer or byte limit, preserve tool and question transitions in order, and flush completion immediately. For the direct host, pass structured arguments to a fixed JavaScript receiver through `callAsyncJavaScript`. For Tauri, one ordered `Channel` per window is a good candidate. JS applies semantic state and schedules visible DOM writes once per animation frame. Minimized windows can catch up with coalesced state or a paged snapshot when they return. A gap triggers resync from Rust, so a slow panel cannot stall agent I/O or accumulate an unbounded queue. [Apple structured JavaScript call](https://developer.apple.com/documentation/webkit/wkwebview/callasyncjavascript%3Aarguments%3Ainframe%3Aincontentworld%3Acompletionhandler%3A), [Tauri channels](https://v2.tauri.app/develop/calling-frontend/#channels), [WebKit power guidance](https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/) (read 2026-11-25).

Use a variable-height virtual list with stable row IDs, a height index keyed by width and template revision, and modest overscan. Hold the first visible row and pixel offset across height changes. Follow new content only while the user is at the tail. Reuse inactive DOM slots while keeping focused, selected, and expanded rows mounted. Make cross-page selection an explicit implementation and benchmark case. Keep the full transcript and find index in the core, page in old rows, and bound the parsed-block, image, and layout caches. Find traverses every row and mounts the hit before applying its highlight. Give VoiceOver a way to ask for older and newer messages and keep its current item mounted. This bounds renderer working memory for inactive history. Persisted data and any in-memory index still scale with transcript size.

Parse Markdown in Rust into safe render blocks. For example, use `pulldown-cmark` for CommonMark and tables, with raw HTML disabled in ordinary blocks. Render via DOM text and typed attributes. Reparse the mutable tail on a bounded cadence, cache committed blocks, and do one definitive parse of the completed message so incomplete fences, table syntax, and later reference definitions resolve correctly. Keep sizing metadata for images, and route file links as opaque references through native UI so a template never gets a general path opener. Preserve copyable code, semantic tables, action counts, thoughts, debate rows, question cards, and pinned charts in the replay fixture. [pulldown-cmark documentation](https://docs.rs/crate/pulldown-cmark/latest) (read 2026-11-25).

Drive row insertion, collapse, pinning, sidebars, and template swaps with 200–350 ms ease-out or spring transitions. Reveal growing content inside a clipped container, retarget a transition from its current dimension, and keep caret, wheel movement, and IME feedback immediate. Keep animation layers limited to active transitions. Use a short opacity fade with `prefers-reduced-motion`. Verify intermediate frames, the height of the clipping region, and the position of the next row while streaming and scrolling. [WebKit reduced-motion media query](https://webkit.org/blog/7551/responsive-design-for-motion/) (read 2026-11-25).

Ship a versioned structured spec for new standard charts, tables, and headline cards. Keep existing `vcx.chart` as an adapter, and bundle a pinned Lightweight Charts build with its required attribution so ordinary charts work offline. Supply a data-table equivalent and a static preview where practical. Keep free-form HTML as an opt-in live surface within the same transcript. A sandboxed iframe with only `allow-scripts` is the first design to validate. Instantiate on visibility or expansion, cap the active budget, and dispose frames and polling subscriptions when they leave it. Preserve original chart source in old threads. Render a preview on demand or on idle, and provide an isolated expanded viewer for legacy charts that need continued interaction. [Lightweight Charts licensing and distributions](https://tradingview.github.io/lightweight-charts/docs/5.0), [HTML iframe sandbox](https://html.spec.whatwg.org/multipage/iframe-embed-object.html) (read 2026-11-25).

## 4. Disk template and trust boundary

Keep a signed default bundle in the app and watch one separate user-owned folder for a manifest, HTML, CSS, JS, and local assets. Debounce editor writes, validate manifest and contract versions, reject path escapes, and copy the complete candidate into an immutable directory identified by its content hash. Stage it in a disposable unshown system WKWebView with fixtures, no privileges, a startup deadline, and a contract handshake. Run a short smoke test for row rendering, find, focus, and required input and chart slots. Apply a successful CSS-only edit in place. For an HTML or JS change, stage the revision before promoting it to each window. Keep the last working copy independently of the editable folder and offer a native revert action. Use a startup and crash watchdog to roll a failed revision back, including failures that depend on a particular real transcript. Directory-level notifications can cover atomic-save editors. [Apple FSEvents architecture](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/TechnologyOverview/TechnologyOverview.html) (read 2026-11-25).

Keep drafts, attachment references, undo where supported, and pending question IDs with the trusted host. For each open window, capture the scroll anchor, follow mode, find and disclosure state, native focus, and transcript selection as stable row/block IDs and character offsets. On promotion, hydrate through a known sequence, catch up to the current one, materialize the saved anchor and selection, then show the page. Defer disruptive reloads until IME composition, a selection drag, or an active chart gesture finishes. If a changed template removes a selection endpoint, keep that window on its prior revision until the selection clears. Keep the native composer mounted through all of this.

Treat editable HTML and JS as untrusted even when a local agent saved it. A signed bootstrap and native host own actions that can send prompts, switch providers, open files, access attachments, or affect workers. Bind each renderer instance to a read-only, session-scoped view of the transcript. Its inputs to the host are limited typed requests for paging, sizing, and view state. Give it no generic shell, process, filesystem, updater, or worker RPC capability. Keep user activation for privileged actions in trusted controls, including link or question actions that delegate to the agent. Apply a local-resource-only navigation and CSP policy to the template. Keep external network, file navigation, popups, and downloads closed, and serve assets through a path-constrained resolver. Check frame identity, origin and session at the bridge. An isolated WebKit content world helps protect the bootstrap's JS globals. Keep privileges outside any shared DOM. Tauri deployments should also explicitly restrict command permissions and avoid exposing privileged plugins through webview capabilities. [Apple content worlds](https://github.com/WebKit/webkit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKContentWorld.h), [Apple frame identity](https://developer.apple.com/documentation/webkit/wkframeinfo), [Tauri capabilities](https://v2.tauri.app/security/capabilities/) (read 2026-11-25).

Give chart frames an opaque origin, a deny-by-default resource policy and no native bridge. Reject external navigations at the host, including frame self-navigation. Use a frame-bound message port or verify the sending frame plus a per-instance token, and schema-check each message. Preserve `vcx.live` through a broker that maps each chart to approved endpoints or opaque feed IDs. Apply response size, polling, timeout and concurrency limits, check redirect destinations and actual resolved addresses, and send no ambient credentials. The owner's approved local feeds can use explicit bindings. A chart gets only its own feed data. This also keeps an agent-edited template from turning a chart proxy into a transcript upload path. [HTML iframe sandbox](https://html.spec.whatwg.org/multipage/iframe-embed-object.html), [HTML cross-document messaging](https://html.spec.whatwg.org/dev/web-messaging.html) (read 2026-11-25).

## 5. Shippable migration

1. **Record the baseline and spike the transcript.** Replay an actual anonymized 5,000-row session with recorded timing and charts. Take the same fixture through a small unshown system WKWebView in the current signed host. Keep a native transcript switch and ship the web transcript behind it after the first gate. This delivers immediate styling without moving input or workers. Validate both one and eight windows, plus the no-window interaction path.
2. **Ship the disk template and chart migration.** Add staged reload and recovery, the data spec, and compatible isolated legacy charts. Keep the native viewer available for rollback. Test reloading during streaming, a dirty composer, IME and selection, simultaneous window updates, a bad edit, frame destruction, both wheel targets of expanded charts, and chart behavior with offline and approved live data.
3. **Move model and worker code behind the existing contracts.** Start with Rust replay, transcript reduction, and Markdown parsing, then one provider worker at a time. Release each adapter only after mixed-version replays and real provider smoke tests cover the original CLI, hooks, approvals, question IDs, cancellation, restart and handover. Keep Fleet reporting and the task/status/sidebar feature checks in the signed app. Move the host from Swift only if that reduces maintenance after these releases. Carry forward the bundle ID, signing identity, entitlements, global shortcuts, menus and macOS responders. Keep the present Command Line Tools build and signed `.app` workflow as the control, and compare designated requirements and real TCC-granted behavior when replacing the binary. [Apple signing requirements and `codesign`](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements?changes=_3), [Apple distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac?changes=la) (read 2026-11-25).

For every release, compare fixed seeds and identical window sizes and rendering loads at one and eight windows. Measure host and helper physical footprint separately and in aggregate, with workers and children listed independently. Capture idle, warm scrolling, concurrent streaming, repeated opening/closing and reload peak, CPU/GPU work and energy on battery. Record p95 frame intervals, missed frame budgets and input-to-paint for a scroll gesture, keystroke and first token. A proposed initial gate is p95 frame work within 16.7 ms at a 60 Hz test budget, p95 key-to-paint within 50 ms, at most a 10% regression in measured eight-window frontend footprint and energy, and a recoverable renderer crash or bad template during an active turn. These are proposed budgets. If WebKit exceeds them after bounded views, chart eviction and idle suspension, keep the opt-in web transcript and defer the default switch. Claim RAM savings only when repeated matched runs show a reduction beyond run-to-run variance. Headless frame workload is a proxy for actual compositor drops. Route tests through unshown real windows and observe the release build during normal owner use to confirm display-frame pacing, without opening a checking window. [WebKit power guidance](https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/), [GPUI headless timing limitations](https://github.com/zed-industries/zed/blob/main/.agents/skills/gpui-bench/SKILL.md) (read 2026-11-25).

## 6. Risks and cost

The highest memory risk is several live WebContent processes plus decoded images and active charts. Background chart timers, repeatedly reparsing a large Markdown tail and animating entire lists can turn into steady CPU or GPU work. The most expensive correctness bugs will be input and lifecycle boundaries. Test shortcuts during marked text, paste and attachment handling, modifier precedence, selection across virtual rows, VoiceOver reading and focus, wheel routing on chart controls and blank areas, and a hot reload at the same moment as a user edit. Keep the native composer until equivalent behavior is verified. [WebKit power guidance](https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/), [WKWebView responder issue](https://bugs.webkit.org/show_bug.cgi?id=249976) (read 2026-11-25).

Estimate for one developer working with AI agents is 2–4 weeks for a usable web transcript and reload, 3–5 more for chart compatibility, input and deployment parity, and 4–7 more for Rust model/worker migration and mixed-version hardening. Total estimate is 9–16 developer weeks for the staged hybrid, with 2–4 additional weeks as an estimate for replacing the AppKit host if it proves worthwhile. Keep the existing checks executable through the overlap. Extract their fixtures and expected behavior into reusable event traces, differential-test Swift and Rust, port view assertions to DOM/AX and native event tests, and keep the `--render` and `--render-demo` outputs in the release checks. Track coverage by behavior before retiring any old check. The proposed architecture uses local execution and offline assets for the standard viewer.
