Recommend wry and tao directly, not full Tauri and not a native Rust UI kit, for the Rust frontend.
Keep one Rust frontend process, one shared WKWebsiteDataStore, one WKWebView per window, and keep the separate runtime workers.
Accept that this will probably use more RAM than the current 253 MB Swift frontend for 7 windows, and prove the shared-process saving in a spike before committing.
Build the display as vanilla HTML, CSS and JS loaded from disk, with Rust-side Markdown, a versioned data contract, and charts in sandboxed iframes.
Ship it in steps, starting with a web transcript inside the current Swift app, then porting the core to Rust only after the spike passes.

Stack

Tauri 2 is the most mature webview choice. Tauri 2 went stable in October 2024 and the current line was 2.11.x in mid-2026, source https://github.com/ericrisco/rsc-harness/blob/HEAD/skills/tauri/SKILL.md read 25 Nov 2026. It uses the system webview, WKWebView on macOS, WebView2 on Windows and WebKitGTK on Linux, and does not bundle Chromium, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/04-tauri.md read 25 Nov 2026. Its binary size claim is 3 to 10 MB for a typical app versus 80 to 150 MB for Electron, source https://github.com/nordeim/maison/blob/HEAD/skills/tauri-2/SKILL.md read 25 Nov 2026. Its security model is useful: Tauri 2 IPC is default-deny, capabilities bind permissions to specific windows, and a webview with no capability has zero IPC access, source https://github.com/agents-inc/skills/blob/HEAD/src/skills/desktop-security-tauri/SKILL.md read 25 Nov 2026. The cost for VCX is abstraction. Tauri owns the window, updater, plugin and IPC shape, it hides the WKWebView, and it makes the existing frontend and worker split and live update harder to keep exactly. Tauri also has no WebDriver or CDP on macOS WKWebView, so Playwright cannot attach to the real app, source https://github.com/andrejvysny/darkroom/blob/HEAD/.claude/skills/tauri-v2-ui-testing/SKILL.md read 25 Nov 2026, and tauri-driver is Windows and Linux only because macOS has no WebDriver for WKWebView, source https://tutorialscenter.com/tauri/end-to-end-testing-and-ci read 25 Nov 2026.

Wry and tao directly is my recommendation. Wry is a cross-platform WebView rendering library in Rust, it re-exports tao for the event loop and window creation, and on macOS WebKit is native, source https://docs.rs/wry/latest/x86_64-pc-windows-msvc/wry/ read 25 Nov 2026. The tested Tauri stack in July 2026 used wry 0.55.1, published 2026-05-04, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/04-tauri.md read 25 Nov 2026. Direct wry gives VCX what Tauri hides: one WKWebViewConfiguration per app, one cached WKWebsiteDataStore, one custom scheme for vcx:// assets, direct evaluateJavaScript, direct takeSnapshot for offscreen renders, and direct control of page visibility and process suppression flags. It is a thinner dependency surface, it keeps the Rust core in charge of the socket RPC to workers, and it lets the template be a plain file on disk rather than a bundled frontendDist. The price is that VCX must write its own window management, menu, tray, updater, capability allowlist and signing glue, all of which Tauri would partly supply. For a macOS-only, single-user app that already has those pieces in Swift, that price is lower than fighting Tauri's model.

A Swift or Rust shell around one shared WKWebView is the same engine with a different owner. It is the right first migration step, not the final stack if the goal is Rust. A Swift AppKit shell using NSWindow and WKWebView avoids the SwiftUI scroll and focus bugs in the brief, keeps the current signing and TCC path, and can share one data store across windows. A Rust shell using objc2 or wry does the same with less Swift left. Either way the RAM story does not change, because the engine is still system WebKit. The brief measured One Text, a Tauri 2 app, at about 480 MB total on 19 Nov 2026: 76 MB app process, 315 MB WebKit WebContent, 83 MB WebKit GPU and 7 MB WebKit networking. That is the measured cost of the WebKit helper processes, and it is the main reason a webview does not save RAM by itself.

Dioxus desktop is not a different engine. Dioxus desktop 0.7.9 is described as a WebView renderer for Dioxus, it renders into the system webview via wry with windowing from tao, the exact same two crates Tauri is built on, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/07-dioxus.md read 25 Nov 2026. Dioxus 0.7.9 was the latest stable on crates.io, published 2026-05-08, with 0.8.0-alpha.0 published 2026-05-19, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/07-dioxus.md read 25 Nov 2026. It adds a Rust RSX UI model and no JS toolchain, but it adds a framework, a CLI, telemetry questions and version skew against Tauri's wry and tao, while keeping the same WebKit RAM. Dioxus Native and Blitz are not ready for this job. Blitz is described as beta, usable for early adopters willing to live on the bleeding edge, with many bugs and missing features, source https://threatcluster.io/article/dioxus-labs-blitz-1a39efdb read 25 Nov 2026. An earlier July 2026 survey said Blitz was pre-alpha and that its authors would not yet recommend building apps with it, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/data/stack-rows.md read 25 Nov 2026. Blitz has no JS engine, so free-form agent HTML and JS charts would need a separate JS runtime or a data-only chart spec, and its CSS, text and accessibility coverage is still incomplete for a daily driver chat app.

GPUI is the fastest native option and the wrong fit for the stated goal. GPUI is Zed's GPU-accelerated UI framework, it draws its own interface with the GPU instead of embedding a browser, source https://www.ithub.directory/web-frameworks/gpui read 25 Nov 2026. The newest release was 0.2.2 from 22 Oct 2025 and it was still the latest release as of 7 July 2026, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/03-gpui.md read 25 Nov 2026. It has low-level elements including uniform_list virtualization, but no first-party high-level widget or text-input library, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/03-gpui.md read 25 Nov 2026. Input methods are a clear gap in recent use: text from an input method arrives once it is committed, but nothing is shown while it is still being composed, unless the field implements GPUI's input-handler trait, source https://mah3uz.com/blog/gpui-after-three-apps read 25 Nov 2026. GPUI would give low RAM and excellent scrolling, but it would force VCX to rebuild Markdown, tables, images, links, find, selection, IME and accessibility from scratch, and it would not give the hot-reload HTML template the owner asked for.

Slint, iced and egui are serious native kits, but they trade the web display away. Slint 1.17.1 was verified on 7 July 2026, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/06-slint.md read 25 Nov 2026, and Slint 1.18 was released 16 Sept 2026 with screen reader support for text input, source https://rebrand.slint.dev/blog/slint-1.18-released read 25 Nov 2026. Slint integrates AccessKit by default on the Winit desktop path, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/06-slint.md read 25 Nov 2026. It is mature, but its UI is a .slint DSL compiled to Rust, not HTML, so a display tweak still needs a rebuild and free-form agent charts need a native chart renderer. Iced 0.14.0 was released 7 Dec 2025, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/01-iced.md read 25 Nov 2026, and AccessKit is not integrated in stable iced, with no accesskit dependency in the 0.14.0 workspace, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/01-iced.md read 25 Nov 2026. A July 2026 spike found iced 0.14 ships no AccessKit and no accessibility tree, source https://docs.cairn-ehr.org/spikes/0004-iced-reference-ui-viability/ read 25 Nov 2026. Egui is different: egui 0.37.0 was published 15 Oct 2026, source https://www.ithub.directory/web-frameworks/egui read 25 Nov 2026, and egui includes optional AccessKit support, enabled by default in eframe, source https://lib.rs/crates/egui read 25 Nov 2026. Egui is immediate mode, fast for tools, but it lays out large scroll areas every frame, it has no paragraph-level BiDi, and it would still need a custom Markdown, table, image and chart layer. None of these three gives a hot-reload HTML template or a JS chart engine for free.

Sciter and Ultralight are the small HTML engines, and both fail on fit. Sciter is an embeddable HTML, CSS and script engine in a compact single file of 4 to 8 MB, source https://pypi.org/project/PySciter/0.4.15/ read 25 Nov 2026. Sciter.JS uses standard JavaScript via QuickJS, source https://copyprogramming.com/howto/rendering-ui-with-sciter-on-top-of-the-window read 25 Nov 2026, but its CSS is a subset, its script engine is not V8 or JavaScriptCore, its Rust bindings are thin, and it is closed source. Ultralight is a stripped-down single-process port of WebKit, source https://ultralig.ht/ read 25 Nov 2026, with base memory on macOS of 17 MB versus 97 MB for Electron in its own comparison, source https://www.gitplanet.com/project/ultralight read 25 Nov 2026. Its core renderer is proprietary, only part of its WebCore is LGPL on GitHub, source https://www.gitplanet.com/project/ultralight read 25 Nov 2026, and it is free for non-commercial use and for commercial use by companies with less than 100k dollars gross annual revenue, source https://www.gitplanet.com/project/ultralight read 25 Nov 2026. It would save RAM, but it adds a C++ dependency, a proprietary core, a WebKit fork lag, and no first-class Rust shell. It is a spike candidate only if the shared WebKit spike fails badly and the owner accepts a proprietary engine.

For keyboard focus, IME, text selection and accessibility, the webview options inherit the browser stack, which is the strongest of the group. The native kits vary: Slint and egui have AccessKit by default, GPUI's AccessKit plumbing was merged but unreleased in 0.2.2 and disabled by Zed in the July 2026 survey, source https://github.com/goldstrikearch/rust-gui-desktop-ecosystem-state/blob/HEAD/report/20-how-to-build.md read 25 Nov 2026, and iced has none in stable 0.14. For a keyboard-first chat app with a composer, find bar and long transcripts, that difference matters more than raw frame rate.

Windows and processes

Use one webview per window, in one frontend process, with all windows sharing one data store. Do not use one process hosting all windows as separate tabs in a single page, and do not use a single window with tabs unless the owner explicitly wants tabs. One webview per window keeps the existing mental model, one window per agent session, keeps window management, focus, drag, Mission Control and Fleet reporting simple, and keeps a crash or hang in one page from taking down the other windows' DOM state in the same way a single page would. A single page with tabs would also make scroll position, selection, composer state and pinned charts per session harder to isolate, and it would make live update per window harder.

The process sharing question needs a correction to the old mental model. WKProcessPool is deprecated in macOS 12.0 and iOS 15.0, and creating and using multiple instances no longer has any effect, source https://github.com/abhishakenp/den/blob/HEAD/docs/research/apple-platform.md read 25 Nov 2026. Apple lists processPool on WKWebViewConfiguration as deprecated, source https://developer.apple.com/documentation/webkit/wkwebviewconfiguration read 25 Nov 2026. What decides sharing now is the data store: web views that share a WKWebsiteDataStore share WebKit's network and content processes, and web views with different stores do not, source http://dev.to/kylmora/six-things-about-wkwebview-the-docs-dont-tell-you-3c08 read 25 Nov 2026. That source also warns that WKWebsiteDataStore forIdentifier returns a new object every time, so the app must cache one object and hand the same object to every window, or sharing is silently lost, source http://dev.to/kylmora/six-things-about-wkwebview-the-docs-dont-tell-you-3c08 read 25 Nov 2026. The den research notes the same sharing claim but marks it unverified against Apple docs, source https://github.com/abhishakenp/den/blob/HEAD/docs/research/apple-platform.md read 25 Nov 2026, so VCX must measure it on this Mac rather than trust it.

In practice, expect one shared WebContent process for the chat pages if they share a store and a site, plus one shared Networking process and one shared GPU process, similar to the One Text measurement in the brief. Expect a second WebContent process only if WebKit isolates a chart iframe origin, a different site, or a heavy page, or if a WebContent process crashes and WebKit restarts it. Do not assume one WebContent process per window. That old assumption would make 8 windows unaffordable: 8 times 315 MB would be over 2.5 GB, estimate, and it is not what the One Text total suggests. The spike in section 5 must list processes with footprint while opening 1, 4 and 8 windows on the same thread, and it must open a chart-heavy thread to see if iframes split processes.

Keep the frontend and worker split. The brief says the frontend is 253 MB with 7 windows on 25 Nov 2026 and each runtime worker is 11 to 22 MB, and the frontend can be replaced without killing agents because each agent session lives in its own worker that owns the agent CLI child. That split is the right shape for a Rust core too. Keep the Rust frontend as the window owner and the Rust workers as session owners, talking over the existing local socket RPC. Keep live update: the auto-update job builds each push to main, every open window moves to the new frontend build once its turn ends, and workers swap later. The only change is that the new frontend must be able to reattach to existing workers and resync transcript state, scroll position and composer text from the worker or from a per-session state file, rather than asking the worker to restart the agent. If the template reloads, the frontend must not restart the worker. If the frontend binary swaps, the new frontend must not restart the worker either. Keep Fleet as a separate menu-bar app that receives state reports from the frontend, not from the web pages, so a template bug cannot break Fleet reporting.

Rendering and streaming design

Tokens should flow from the Rust core to the page in one direction, in batches, on animation frames. The worker sends token deltas to the frontend over the socket. The frontend appends them to a per-session append-only log in Rust, with a stable row id, a kind, a timestamp and a compact payload. It does not send each token to JS as a separate evaluateJavaScript call. It coalesces deltas for up to one frame, about 16 ms at 60 fps, estimate, and sends one JSON batch per window per frame. JS applies the batch to the current streaming row only, it does not re-render the whole transcript. When the agent finishes a row, Rust marks the row sealed and JS freezes its height. That keeps the DOM work proportional to the new text, not to the transcript length.

Use a virtualized list with DOM recycling. Keep 5,000 rows in Rust memory as structured rows, not as 5,000 live DOM nodes. In the page, keep only the visible rows plus a buffer above and below, about 30 to 60 rows total, estimate, and recycle those nodes as the user scrolls. Each row needs a measured height cache in JS, keyed by row id and width, so scroll height stays stable when rows above change. Use scroll anchoring: when new content grows above the viewport, adjust scrollTop by the growth, and when the user is pinned to the bottom, keep them pinned. Use content-visibility auto on rows outside the viewport as a second guard, not as the only virtualization, because it does not reduce DOM node count by itself. Keep images lazy, keep code blocks collapsed by default only if the user asked for it, and keep tool call blocks as one collapsed node per answer with a count that updates in place. For find, do the search in Rust over the structured log, return match row ids and offsets, and let JS highlight only the visible matches, then jump to the next match by scrolling the virtual list to that row id.

Render Markdown in Rust, not in JS. Comrak is a CommonMark and GitHub Flavored Markdown compatible parser and renderer, written in Rust, compliant with CommonMark 0.31.2 by default, source https://github.com/kivikakk/comrak read 25 Nov 2026. Pulldown-cmark is a pull parser for CommonMark, written in Rust, with optional support for footnotes, GitHub flavored tables, task lists and strikethrough, source https://fastly-app.crates.io/crates/pulldown-cmark/0.10.3 read 25 Nov 2026. Either works, but Comrak is the better fit for tables, task lists and strikethrough in one place. Rust should parse Markdown incrementally for the streaming row, emit sanitized HTML with an allowlist, and send that HTML to JS. JS should not parse Markdown and should not use innerHTML on raw agent text. Sanitization must strip script, iframe, object, embed, form, meta, link, style with URL, and event handler attributes, and it must rewrite local file links to a vcx://file route that Rust validates against an allowlist. Images from the agent should be served through the same custom scheme, with a size cap, estimate 10 MB per image, and a decoded size cap in JS. Keep the raw Markdown in Rust for find, copy and re-render, and keep the HTML as a cache, not as the source of truth.

Keep long transcripts fast and memory flat by capping what the page holds. Rust keeps the full log on disk per session, with an in-memory window of recent rows, estimate 500 rows, and a spill file for older rows. JS keeps only visible rows plus a small cache of recently visible rows. When the user scrolls far back, JS asks Rust for that row range by id, Rust returns the sealed HTML, and JS swaps it in. Do not keep a growing string of all HTML in JS. Do not keep all images decoded at once. Use a ResizeObserver on the chat container to invalidate the height cache on width change, and use a single rAF loop for scroll, resize and streaming updates, not three separate loops.

Charts fit in sandboxed iframes, with a data-only spec as the preferred path. A chart block should be an iframe with sandbox set to allow-scripts only, no allow-same-origin, no allow-top-navigation, no allow-forms, and no access to the VCX bridge. The iframe loads from a vcx://chart/<id>/ URL served by Rust from a sealed chart payload, not from a file path the page can guess. The parent page and the iframe talk only by postMessage with a chart id and a typed message, and the parent never forwards bridge calls into the iframe. For the helper, keep vcx.chart as a data call, not as free-form JS. The template receives {v: 1, kind: "line", data: [...], x: "time", y: "price", title: "..."} and draws it with a vendored copy of lightweight-charts, not a CDN. Lightweight Charts is a free open-source client-side library, 45 KB in size, source https://www.tradingview.com/charting-library-docs/latest/product-comparison read 25 Nov 2026, and version 5.0 reduced the base bundle to 35 kB, source https://github.com/tradingview/lightweight-charts/releases/tag/v5.0.1 read 25 Nov 2026. Vendoring it removes a network dependency, removes a CDN failure mode, and lets the template work offline. For free-form agent HTML, keep it but isolate it: the agent writes a fenced HTML block, Rust extracts it, stores it as a chart payload, and renders it only inside the sandboxed iframe. If the agent HTML tries to call the bridge, fetch a local URL, or navigate the top page, the sandbox blocks it. Pinned charts should be the same iframe moved above the chat, not a second copy, so pinning does not double memory. Expanded charts should resize the iframe container with an animation, not reload the iframe.

The vcx.live bridge should be a Rust fetch, not a JS fetch. The chart page posts {type: "live", url: "...", seconds: 5} to the parent, the parent validates the URL against an allowlist of hosts and schemes, Rust fetches it, and Rust posts the result back. The chart page never gets a direct network capability and never gets the user's local file access. Polling should be capped, estimate one poll per 5 seconds per chart, and paused when the chart is offscreen or the window is hidden.

The hot-reload template

Structure the template as one watched folder, not as a file inside the binary. Use a folder like ~/Library/Application Support/VCX/template/ with manifest.json, template.html, template.css, template.js, vendor/lightweight-charts.js, and a README for the contract. Manifest.json carries {template_version: 3, contract_version: 2, name: "default", entry: "template.html"}. The Rust core reads the manifest, checks contract_version against the version it supports, and refuses to load a template with a newer contract it does not understand. The template is vanilla JS, no build step, no npm, no framework, so a change to CSS or JS shows at once. Keep the template in git, with a last-good copy in the app bundle and a user copy on disk, and keep a hash of each file so the frontend can tell if the file changed on disk or in the bundle.

The data contract between Rust and the template must be stable and typed. Define it once in Rust as serde structs and in JS as a JSDoc type, and test it in both directions. The contract has four messages. Init: {type: "init", contract: 2, session: {id, title, project}, theme: "dark", reduceMotion: false, rows: [...], composer: {text, chips: []}, scroll: {rowId, offset}}. Append: {type: "append", rows: [{id, kind, html, state}]}. Patch: {type: "patch", id, html, state, count}. Event from JS to Rust: {type: "event", name: "send", "pick", "find", "pin", "expand", "open-file", payload: {...}}. No other message shapes are allowed. The template must not invent a new Rust method, and Rust must not send a field the template does not expect without bumping contract_version. Version the contract, not the template alone, so an old template can keep working with a new core for at least one contract version, estimate.

Reload without losing state by separating state from presentation. Rust owns scroll position, selection, composer text, find query, pinned chart ids and expanded ids. JS owns only DOM nodes and animation state. On reload, Rust sends init with the current scroll row id and offset, the composer text and chips, the find query and matches, and the pinned and expanded ids. JS rebuilds the visible window from that init, restores scrollTop from the row id and offset, restores the composer textarea value and focus if it had focus, and restores selection by row id and character offsets if the selection was inside the transcript. For a live streaming row, Rust pauses the batch for one frame during reload, then resumes with the next batch, so no token is lost. For animation, reload should be a fade, not a jump, and Reduce Motion should make it a short fade, about 100 ms, estimate.

Fall back when an edited template is broken. Keep three copies: the running copy in memory, the last-good copy on disk, and the bundled copy in the app. On file change, Rust validates the template before applying it: it checks manifest JSON parses, contract_version is supported, template.html parses, template.js parses with a JS parser in Rust or by loading it in a hidden WKWebView first, and template.css parses without an error that would blank the page. Then it does a test render in a hidden WKWebView, offscreen, with a small fixture thread, and it takes a snapshot. WKWebView takeSnapshot still produces correct PNGs when the window is offscreen, with alpha 0 and ignoresMouseEvents, source https://chatoverflow.dev/n/run-macos-wkwebview-test-harnesses-invisibly-but-still-rendering-05b65ad2a097 read 25 Nov 2026. If the test render throws, times out after 2 seconds, estimate, or produces a blank image, Rust keeps the running template, shows a small error in the status bar with the file and line, and writes the error to a template log. It does not apply the broken edit to any window. If a template passes validation but breaks in a real window, for example by throwing on a real row kind, Rust catches the JS error via the bridge, reverts that window to the last-good template, and keeps the other windows on the last-good template too. The user can then fix the file and reload again.

Keep agents from breaking the main tool with a bad edit by making template edits a gated action, not a silent file write. An agent may propose a template change, but it may not apply it directly to the live folder. It writes to template/drafts/<name>/, Rust validates the draft, renders the fixture, and shows a diff and a preview in a test window. The owner approves the draft with a key or a button, and only then does Rust copy it to the live folder and bump template_version. The template itself has no shell, no file write, no network fetch except through vcx.live, and no access to the worker socket. The bridge allowlist is fixed in Rust: send, pick, find, pin, expand, open-file, set-composer, and report-error. Open-file validates the path against the project root and the user's home allowlist, and it opens the file with the system opener, it does not execute it. No bridge method takes a shell command, a path outside the allowlist, or a URL outside the allowlist. The template and chart pages must not be able to run arbitrary local commands through the IPC bridge, because the bridge does not expose a command runner at all. Add a Content Security Policy on the vcx:// page: default-src 'self', script-src 'self', style-src 'self', img-src 'self' data:, connect-src 'none', frame-src vcx://chart/. That policy blocks remote scripts, remote styles and remote fetches even if the template tries them.

Migration path in shippable steps

Step 0 is a spike, 3 to 5 days, estimate. Build a minimal wry and tao app with one shared WKWebsiteDataStore, 8 windows, and the same 5,000-row thread from the current app. Measure with footprint and top: total RAM at 1, 4 and 8 windows, WebContent process count, scroll frames per second while streaming, input latency from keypress to composer echo, and time to first paint. Also measure the same thread in the current Swift app for comparison. Stop if the shared store does not share a WebContent process and 8 windows exceed 700 MB total, estimate, or if scrolling drops below 50 fps on a sustained stream, estimate, or if input latency exceeds 50 ms, estimate. Those are stop thresholds, not targets. If the spike fails, do not proceed to a full rewrite. Reconsider a native kit for the transcript and keep charts in a single WebKit view, or keep Swift and fix the SwiftUI bugs with an AppKit shell.

Step 1 is a web transcript inside the current Swift app, 3 to 4 weeks, estimate. Keep the Swift core, workers, Fleet and live update. Replace only the transcript view, the SwiftUI LazyVStack and per-block WKWebViews, with one WKWebView per window using the same shared data store. Keep the composer, task bar, status bar and sidebar in Swift for now. Port the Markdown rendering to a small Rust helper or keep it in Swift for this step, but define the row JSON contract that the Rust core will later use. Measure the same numbers as the spike, plus focus theft, wheel events over an expanded chart, and pinned block height. Stop if the web transcript is slower than the Swift transcript on the same thread, or if focus or wheel regressions cannot be fixed in the AppKit shell. This step is shippable on its own: the owner gets hot-reload for the transcript template and a smoother scroll path without a Rust rewrite.

Step 2 is the Rust core behind the Swift shell, 6 to 8 weeks, estimate. Port session management, worker spawning, socket RPC, CLI drivers for Claude Code, Codex and Ollama, and the headless browser debate path to Rust. Keep the Swift shell talking to the Rust core over the same socket, so the Swift UI does not need to change. Port the 7,500 lines of checks in two parts: Rust unit tests for the core, and template contract tests that run the template in headless Chromium with a mocked bridge. Measure worker RAM, CLI spawn time, streaming latency from worker to page, and check pass rate. Stop if the Rust core cannot match the Swift core's streaming latency or if a CLI driver loses a hook, skill or MCP behaviour that the Swift core had. This step is shippable: the owner gets a Rust core with the same Swift display.

Step 3 is the Rust shell, 3 to 4 weeks, estimate. Replace the Swift shell with wry and tao, keeping the same template, contract and worker protocol. Keep Fleet as a separate Swift menu-bar app for now, because it is small, it already works, and it isolates menu-bar and global hotkey code from the main rewrite. Measure total RAM at 8 windows, cold start, live update swap time, and offscreen render time. Stop if the Rust shell cannot do offscreen takeSnapshot renders or cannot keep windows hidden during tests, or if global hotkeys or TCC prompts regress. This step is shippable: the owner gets the full Rust plus web display stack.

Step 4 is hardening and live update, 2 to 3 weeks, estimate. Port the remaining headless interaction checks to drive real mouse and key events into unshown windows via the Rust shell, add the template draft and approval flow, add the last-good fallback, and add the per-window live update reattach path. Measure check time, template reload time, and time from push to main to all windows on the new build. Stop if check coverage drops below the current level or if live update kills a worker. Total for steps 0 to 4 is 14 to 20 weeks elapsed for one developer working with AI agents, estimate, assuming the template and contract are defined in step 1 and not redesigned in step 3. That range is an estimate, not a commitment, and it assumes no new feature work during the rewrite.

What to keep in Swift, if anything: keep Fleet as Swift for now, keep a tiny Swift helper for global hotkeys and for any TCC permission that needs an AppKit entitlement, and keep the existing signing script. Signing without Xcode is already proven by the current app, which is built without Xcode using Command Line Tools and SwiftPM only. Codesign with --force --options runtime --timestamp and --sign with a Developer ID Application certificate, and notarize with notarytool, are command-line steps, source https://skills.lc/kjetilge/macos-distribution/kjetilge-macos-distribution-skills-macos-distribution-skill-md read 25 Nov 2026. The Rust .app bundle can use the same script, with the same entitlements file, and the same hardened runtime flag. Do not keep SwiftUI for the transcript, and do not keep a Swift shell long term if the Rust shell passes step 3, because two shells double the maintenance.

Risks and costs

RAM is the largest risk. The current frontend is 253 MB with 7 windows, peak 305 MB, on 25 Nov 2026, from the brief. One Text is 480 MB total, from the brief on 19 Nov 2026. A shared WebKit process will probably put VCX at 400 to 550 MB total for 8 windows, estimate, even if the Rust core is only 30 to 50 MB, estimate. That is a regression, not a saving, and the owner should accept it explicitly before step 2. If RAM is a hard cap at the current level, the web display direction is wrong and a native kit should be chosen instead. Energy is a second risk: WebKit GPU and WebContent processes wake on rAF, timers and animations. Mitigate by pausing rAF and polling in hidden windows, by batching streaming to one frame, and by using CSS transforms and opacity for animations rather than layout. Input latency is a third risk: a keypress now goes through WebKit, JS, the bridge and Rust, instead of through NSTextView. Mitigate by keeping the composer as a plain textarea, by handling number keys and slash commands in JS without a round trip to Rust, and by measuring keypress to echo in the spike. IME is a fourth risk in native kits, but in a webview it is handled by WebKit, which is an advantage for wry over GPUI and iced.

Accessibility regressions are a real risk if the template does not set roles, labels and focus order. The webview gives a browser accessibility tree for free, but the template must use it: the transcript should be a list with row roles, the composer should be a labelled textarea, question cards should be buttons with a number key hint, and tool call blocks should be a button with expanded state. Test with VoiceOver on macOS in step 1, not at the end. Focus theft is a known pain point in the brief, and it must be tested explicitly: clicking a chart, expanding a chart, pinning a chart, and opening the find bar must not steal focus from the composer, and closing them must return focus to the composer.

The rewrite size is 22,100 lines of Swift plus 3,000 lines of Python, from the brief. That is not a line-for-line port. The Rust core will be smaller for session and RPC code, larger for Markdown and template handling, and the template will be a new codebase of vanilla JS, estimate 2,000 to 3,000 lines. The 14 to 20 week estimate in section 5 covers the port, the template, the spike, and hardening, but it does not cover new features, and it assumes the owner reviews drafts quickly. The main cost is not typing, it is the long tail of focus, wheel, IME, find, selection, pinned charts and live update edge cases that the current Swift app already handles.

Keep the 7,500 lines of checks' value by splitting them, not by deleting them. Port Rust unit tests for the core, keep the socket RPC contract tests, and port the UI checks to three layers: template contract tests in headless Chromium with a mocked bridge, because Playwright cannot attach to the real macOS WKWebView, source https://github.com/andrejvysny/darkroom/blob/HEAD/.claude/skills/tauri-v2-ui-testing/SKILL.md read 25 Nov 2026; WKWebView snapshot tests offscreen with takeSnapshot, source https://chatoverflow.dev/n/run-macos-wkwebview-test-harnesses-invisibly-but-still-rendering-05b65ad2a097 read 25 Nov 2026; and a small set of real interaction checks that route mouse and key events into unshown windows, as the current app does. A check that only tests the template in Chromium is not a check of the real app, and a check that only tests Rust is not a check of the display. Both layers are needed, and the check suite should fail the build if either layer drops below the current pass rate.
