Recommendation

Build the Rust tao plus wry frontend first against the existing Swift workers on the v1 socket protocol, because that gives a usable window early and tests the riskiest part, the web display, while the proven session and agent code keeps running.
Extract a shared Rust core library in the same first slices for typed protocol, session model and Markdown, but do not make it a standalone months long project before any window exists.
Build Rust workers second, under the Swift frontend first for conformance, then as the default, with cold takeover from checkpoint and provider history, not live file descriptor takeover.
Keep the native NSTextView composer through objc2, keep the frontend worker split and the lease and sequence rules, and drop the in binary checks and the untyped JSON session model.
Ship v2 of the protocol only after both ends speak v1 in Rust, and stop if the Rust frontend cannot match the Swift frontend on RAM, on 80 ms patch latency, or on snapshot equality for a 5,000 row thread.

Boundaries kept and redrawn

Keep the frontend worker split. The brief gives measured sizes today, frontend 0.31 GB with 13 windows and 7 workers 0.11 GB together, and that split is what lets a frontend restart without killing agents. Keep the Unix stream socket per session in a private 0700 folder with getpeereid peer checking. The getpeereid manual page says it returns the effective user and group IDs of the peer connected to a Unix domain socket, and that it is used to authenticate clients, source https://leopard-adc.pepas.com/documentation/Darwin/Reference/ManPages/man3/getpeereid.3.html read 25 Nov 2026. Keep hello, attach with lease, revision, lastSequence and full state snapshot, perform with strictly increasing sequence and per sequence receipts and fingerprint, detach, list, and session/update with revision and patch, session/leaseLost and runtime/swapping. Those rules are what make a second frontend fail safe instead of splitting a session.

Keep the Connection abstraction in shape, but redraw its type. Today it is start, request with method and params, respond, reject, close, and an event callback of untyped JSON, with each provider adapted to Codex app server shaped events. That shape is right, the untyped JSON is wrong. In Rust it becomes a trait with typed request and event enums, and a passthrough field for provider specific JSON that the core does not need to understand.

Redraw the 2,305 line Session. Split it into vcx-core state, vcx-core turn machine, vcx-core queue, vcx-core draft, vcx-core permissions and usage, and vcx-agents connection handling. The draft must stop being an NSAttributedString with 28 uses. Replace it with a plain struct, text as String, chips as a typed vector with kind, range in UTF-8 byte offsets plus a grapheme index for display, and source path or command name. Only the native composer converts that to attributed string, and only at the AppKit edge.

Redraw untyped JSON everywhere. Use serde typed enums for rows and items, with kind fields as enums, and keep provider payloads as serde_json::Value or serde_json::value::RawValue under an explicit raw field, preserved for round trip and for display, but never used for control flow in the core. Unknown item types must render as a generic notice row, not crash the worker.

Move checks out of the app binary. The 7,668 lines of Check files become Rust unit tests in each crate, protocol conformance tests in vcx-verify that run against both Swift and Rust workers, and page tests in vcx-verify that run against the template. The shipped vcx binary must not contain the check harness.

Coexistence during the move

Two apps, two bundle ids, two settings locations, with a single opt in setting in the Swift app that says use Rust frontend for new windows, default off. Existing sessions stay with the frontend that owns their lease. A new window can be opened in Rust while old windows stay in Swift, because the socket path includes the swap version and session hash, and leaseLost prevents two frontends driving one session. Never auto migrate a live session. A session moves only when the user closes it in one frontend and reopens it in the other, or when the worker is idle and a cold takeover is requested explicitly.

Can a Rust worker take over a running agent from a Swift worker through the existing swap state, pid, file descriptors and unread bytes, and is that worth doing

Technically yes, with SCM_RIGHTS fd passing over the Unix socket, plus a shared freeze format. It is not worth doing first. The Swift freeze returns pid, file descriptors and unread bytes, and the Rust side would need to adopt the exact stdio pipes, preserve the unread byte buffer order, preserve the stream JSON framing state, and handle tokio versus Swift runloop buffering differences. A bug there loses the agent child or corrupts a turn in a way that is hard to reproduce. Do cold takeover first: Swift worker writes a checkpoint, exits cleanly at a turn boundary, Rust worker starts a new agent child and replays rows and history from the checkpoint and provider history. That is already the recovery path, so it gets tested every day. Add live fd takeover only later, as an opt in, if cold restart proves too slow for long running agents, and only with a fallback that kills the adopted child and restarts cold when adopt fails. Effort for live takeover alone is 2 weeks, estimate, and it should not block slices 1 to 5.

Question 3, what to rebuild better, concretely

Protocol. Keep v1 line JSON as is during migration. One JSON object per line, sorted keys, at most 32 MB a frame, 64 MB buffered, with back pressure, as in the brief. Do not switch to protobuf or bincode in v1, because debuggability and Swift interop matter more than wire size while two implementations coexist. For v2, keep NDJSON framing, keep the 32 MB and 64 MB limits, keep sorted keys for fingerprint determinism, and change the envelope to typed JSON with protocol 2 in hello, a schema version per message, a typed error object with code, retryable flag and details, a capability list, and a patch format that carries rowOrder, rowUpdates with item ids, changed items with HTML ids, and draft as typed pieces. Add a heartbeat every 15 seconds, estimate for the interval, and a close reason. Add explicit back pressure signalling, where the frontend can tell the worker to pause patches when the page is busy, instead of relying only on socket buffer full. The reason for a typed v2 is that untyped JSON lets a provider schema change silently break the turn machine, while a typed envelope with a raw passthrough field lets the core reject bad control fields early and preserve unknown provider fields.

State model. Rows become a Rust enum with id, kind as an enum of user, peer, assistant, notice, activity and debate, and items as a vector of typed Item. Items become an enum with variants for CommandExecution, FileChange, McpToolCall, DynamicToolCall, WebSearch, PeerMessage, Reasoning, AgentMessage and UserMessage, each with its own struct, plus a Raw variant that holds the original serde_json::Value and a warning. Use serde with deny_unknown_fields off for provider payloads, and with explicit version fields, so a new field from Claude or Codex does not break deserialization. Keep a revision counter per session, a lastSequence counter, and a fingerprint per perform, as today. Keep the draft out of rows, as a separate Draft struct with text, chips and selection. Keep usage and quota as typed structs, not dictionaries.

How state reaches the page. Full snapshot only on attach. After that, patches batched every 80 ms, as today, coalesced so multiple changes to the same item in one batch send one item update. Markdown HTML is rendered in vcx-markdown in the worker, cached by hash of source plus template version plus renderer options, and sent once per item id. The page caches HTML by item id and reuses it on scroll, on find highlight and on template reload when the hash matches. The page keeps a virtual list, renders only visible rows plus 20 rows overscan, estimate, measures row heights after layout, and keeps a scroll anchor so streaming appends do not jump the view when the user has scrolled up. The Rust to page channel is wry evaluate_script_with_callback for reads and evaluate_script for pushes, but pushes go through a single JSON patch function, window.__vcx_applyPatch, not through many ad hoc scripts, so the page has one entry point to test. The page to Rust channel is wry with_ipc_handler, which receives window.ipc.postMessage strings, source https://docs.rs/crate/wry/0.28.3/source/examples/eval_js.rs read 25 Nov 2026, where the example registers an ipc handler and uses evaluate_script_with_callback. Keep patch size small by sending only changed items, not full rows, and by sending HTML ids instead of resending HTML for unchanged items.

Concurrency. Use tokio in the worker, not in the frontend main thread. Tokio provides a multi thread scheduler that by default starts a worker thread for each CPU core, source https://docs.rs/crate/tokio/1.5.0/source/src/runtime/mod.rs read 25 Nov 2026, and that fits the worker which must drive Claude stdio, Codex JSON RPC stdio, Ollama HTTP and the Unix socket concurrently. Use a multi thread runtime in vcx-runtime with 2 to 4 worker threads, estimate, plus spawn_blocking for checkpoint writes. In the frontend, tao owns the main thread. Tao is a cross platform window creation library, a fork of winit, source https://docs.rs/crate/tao/0.15.8 read 25 Nov 2026, and its event loop must run on the main thread on macOS. Wry evaluate_script must be called on the same thread who created the WebView, source https://docs.rs/wry/0.54.2/wry/struct.WebView.html read 25 Nov 2026, and the docs for WebView say to use EventLoopProxy and a custom event to send scripts from other threads, source https://docs.rs/wry/0.48.1/x86_64-apple-darwin/src/wry/lib.rs.html read 25 Nov 2026. So the frontend pattern is: tao EventLoop with a UserEvent enum, an EventLoopProxy cloned to worker threads, a crossbeam or tokio mpsc channel from socket readers to the proxy, and all wry calls only inside the tao event handler on the main thread. Never call tokio block_on on the main thread, never hold a lock across an evaluate_script call, and never let a socket reader thread touch a WebView directly. The worker side uses tokio, the frontend side uses std threads plus a channel plus the proxy, with a small tokio current thread runtime on a background thread only if HTTP quota calls need it, and that runtime never touches tao or wry.

Template data contract and versioning. The template folder contains a manifest, template.json, with contract version, name, hash of assets, and a list of required page functions, for example applyPatch, applySnapshot, setFind, setQuestionCard, and setStatus. The Rust side validates the manifest on load, checks that the page declares the same contract version through a JS global, and refuses to load a template whose contract is newer than the Rust side understands. Hot reload watches the folder, reloads on change, keeps the last good folder copy in memory, and on a broken edit shows the last good version plus a banner with the error, instead of a blank window. Versioning is semantic for the contract, contract 1, 2, 3, and content hash for assets. A template edit that only changes CSS or JS and keeps the contract can hot reload without a full snapshot, by reapplying the current snapshot. A contract change requires a full snapshot reapply.

Composer. Use a native NSTextView over the web view through objc2, not an in page contenteditable. The reasons are IME, marked text, grapheme handling, undo, spellcheck, drag and drop, and accessibility, all of which AppKit gives for free and a web editor would need to reimplement. The NSTextView is a subview of the tao window content view, positioned at the bottom, with the web view resized above it. The draft model is plain text plus chips, the composer converts chips to NSTextAttachment objects, and on send it converts back to the plain draft struct. The palette is a page overlay, positioned from firstRectForCharacterRange, and the Rust side owns the palette data. If the native composer slips, ship slice 1 with a temporary in page textarea and keep the native composer as slice 3, but do not ship the in page editor as the final composer. The objc2 NSTextView type is MainThreadOnly, source https://docs.rs/icrate/latest/src/icrate/generated/AppKit/NSTextView.rs.html read 25 Nov 2026, so all composer calls stay on the tao main thread.

Live update in a Rust world. Keep the same model as today. The frontend is replaced by a new process that attaches to the same workers, old windows hand over leases, a worker later swaps itself onto the new binary while idle, keeping the agent child and its pipes, and a worker that cannot move keeps its sessions on the old build. In Rust, the updater is a small binary that downloads the new .app, checks a SHA256 hash, replaces the bundle atomically with rename, and restarts the frontend. The worker swap uses the freeze format from slice 6. The frontend must handle a worker that is mid swap by showing a swapping state and retrying attach with backoff, not by dropping the session. Settings stay in ~/Library/Application Support/VCX/settings.json, state in ~/.local/state/vcx, as today, so a rollback to the Swift build still finds its files.

Question 4, what not to port

Drop the Demo window and Demo data. It was useful for SwiftUI layout work, it is not a user feature. Merge TaskBoard and QuotaOverview into the template and status bar, do not keep them as separate native views. Merge Find, Run and the question card host into the page, with Rust owning the data and the page owning the layout. Drop duplicate SwiftUI wrappers around AppKit views, the Rust shell has one tao window and one wry view per session, plus one native composer.

Leave in Swift or Python for now. Leave Fleet, the separate menu bar app, in Swift until the Rust frontend is default, because its protocol is small files and it does not block the move. Leave the Python installer, auto update job, archive and cleanup helpers in Python until slice 7 proves the Rust updater, then port only the updater and the archive helper, and keep the installer script as a thin shell wrapper if it is already reliable. Leave any macOS specific check that only tests SwiftUI layout, and delete it instead of porting it.

What must stay native through objc2 even in the Rust shell. NSApplication activation policy and Dock behaviour, NSWindow traffic lights, collection behaviour and frame, NSTextView composer, NSPasteboard and drag and drop, file open and save panels, accessibility for the composer, global menu, and WKWebView configuration access through the raw handle for snapshot and for occlusion settings. Tao and wry cover window creation and web view hosting, they do not cover those AppKit behaviours, so vcx-objc must own them. Use objc2 and objc2-app-kit, with MainThreadMarker for every call, and gate every private selector with respondsToSelector before calling it.

Question 5, windowless verification with tao plus wry

No window at all is not an option. Wry requires a window type that implements HasWindowHandle, source https://docs.rs/wry/0.48.1/x86_64-apple-darwin/src/wry/lib.rs.html read 25 Nov 2026, where the docs say the webview requires a running event loop and a window type that implements HasWindowHandle, and you can use a windowing library like tao. WKWebView needs an NSView host to render. The correct pattern is a hidden tao window, not no window.

Create the harness as a separate binary, vcx-verify, with NSApplication activation policy prohibited, so it never appears in the Dock and may not create visible windows or be activated. Apple documents prohibited as the application does not appear in the Dock and may not create windows or be activated, and as the default for unbundled executables without an Info.plist, source https://unstuckagents.com/notes/cards/PC-342 read 25 Nov 2026, which quotes the Apple abstracts, and source https://github.com/akurganow/slovo/blob/HEAD/docs/references/menubar-packaging.md read 25 Nov 2026, which lists regular, accessory and prohibited with the same abstracts. Set the tao WindowBuilder with visible false, position the window far off screen at -30000, -30000, set alpha 0, set ignoresMouseEvents true, and order it in with orderBack, never orderFront and never activate. The chatoverflow note on invisible harnesses says to put the NSWindow far off screen, alpha 0, ignoresMouseEvents true, activation policy prohibited, and never orderFront or activate, and that takeSnapshot still works, source https://chatoverflow.dev/n/run-wkwebview-test-harnesses-invisibly-without-throttled-raf-31dffa4a52c1 read 25 Nov 2026.

Load, drive and capture. Load the template through a wry custom protocol or loadFileURL, wait for the page ready signal through the ipc handler, drive state through evaluate_script_with_callback with JSON results, and read the DOM through the same callback, which serializes the evaluation result into a JSON string, source https://docs.rs/wry/0.54.2/wry/struct.WebView.html read 25 Nov 2026. For a picture, do not use a generic screenshot of the window, use WKWebView takeSnapshotWithConfiguration through the raw handle. The API was added as takeSnapshotWithConfiguration completionHandler, source https://trac.webkit.org/changeset/212929/webkit/trunk/Source/WebKit2/UIProcess/API/Cocoa/WKWebView.h read 25 Nov 2026, and it returns the visible viewport contents as an image. In wry 0.57, the macOS web view type WryWebView is exported, source https://docs.rs/wry/0.48.1/x86_64-apple-darwin/src/wry/lib.rs.html read 25 Nov 2026, where the lib exports wkwebview WryWebView, so vcx-objc can get the underlying WKWebView pointer from the tao window NSView hierarchy and call takeSnapshot through objc2. For synthetic input, use two levels. For page logic, dispatch real KeyboardEvent and MouseEvent objects through evaluate_script, with bubbles true and cancelable true, and assert the page handler ran. For the native composer, send NSEvent objects to the NSTextView through the AppKit event path, and for a full key path use CGEventPost only in a dedicated test that owns the input focus, never in the hidden harness that shares the desktop.

Known traps. Timer and requestAnimationFrame throttling in hidden or occluded views is the main trap. WebKit throttles requestAnimationFrame, CSS animations and DOM timers whenever it decides a view is not visible, and an alpha 0 window reports itself as occluded, source https://asyar.org/docs/explanation/launcher-rendering-lifecycle read 25 Nov 2026. A hidden WKWebView throttles setTimeout and setInterval to about 1 Hz, and a 50 ms sampler showed about 950 ms delays, source https://chatoverflow.dev/n/hidden-wkwebview-throttles-js-timers-skewing-perf-probes-1a29de1c335c read 25 Nov 2026. The fix in a harness only is to disable occlusion detection through the private setter _setWindowOcclusionDetectionEnabled, gated by respondsToSelector, and to set the page preferences for inactive scheduling and hidden page timer throttling to false, and to opt out of App Nap with a ProcessInfo activity. The chatoverflow note says to call the private _setWindowOcclusionDetectionEnabled false on the WKWebView, set pageVisibilityBasedProcessSuppressionEnabled and hiddenPageDOMTimerThrottlingEnabled preferences to false, and opt out of App Nap, source https://chatoverflow.dev/n/run-macos-wkwebview-test-harnesses-invisibly-but-still-rendering-05b65ad2a097 read 25 Nov 2026. A correction in the same series says the working KVC key on macOS 26 WebKit is windowOcclusionDetectionEnabled, not _windowOcclusionDetectionEnabled with an underscore, and that the public preferences.inactiveSchedulingPolicy none did not remove the 1 s alignment, source https://chatoverflow.dev/n/run-wkwebview-test-harnesses-invisibly-without-throttled-raf-31dffa4a52c1 read 25 Nov 2026. Treat that private API as harness only, never in the shipped app, and sanity check once against an on screen run. Another trap is that a window that was never ordered in at all can stall iframe init when a backend reply takes 10 s or more, and adding orderBack fixed it, source https://chatoverflow.dev/n/run-wkwebview-test-harnesses-invisibly-without-throttled-raf-31dffa4a52c1 read 25 Nov 2026. So the harness must orderBack, not just create the window. Activation policy is a trap for the shipped app too, where an unbundled binary defaults to prohibited and its window never appears, so the shipped .app must set regular before the first window is ordered front, as in the same source. The Dock icon is a trap in the opposite direction, where the harness must stay prohibited and accessory, while the shipped app must be regular.

How the 7,668 lines carry over. Rust unit tests take the pure logic: Markdown rendering, row and item serde round trip, patch coalescing, draft chip ranges, sequence and receipt idempotency, lease handling, and template manifest validation. Protocol conformance tests take the wire behaviour: hello, attach, perform with increasing sequence, duplicate sequence returns the same receipt, out of order sequence is rejected, detach, list, leaseLost when a second frontend attaches, and recovery from checkpoint. Those tests run as a black box socket client against both the Swift worker and the Rust worker, same fixtures, same assertions, so a pass means the two implementations agree. Page tests take the display behaviour: snapshot of a 5,000 row thread, virtual list DOM count, find, question card, tool call folding, debate row, chart sandbox, and template hot reload with a broken edit falling back to last good. Offscreen renders become snapshot tests in vcx-verify, real mouse and key events routed into unshown windows become JS dispatched events plus NSTextView event tests in vcx-verify, runtime protocol checks become conformance tests, live update checks become swap tests, and archive safety checks become checkpoint round trip tests. Do not port SwiftUI layout checks, they have no Rust counterpart.

Question 6, risks and stop rules

Most likely to go wrong, in order. First, tao plus wry version churn and API drift between the wry version pinned at the start and the version at ship. Notice it early by pinning exact versions in Cargo.lock, by running vcx-verify --smoke on every dependency update, and by reading the wry changelog before bumping. The wry changelog shows 0.57.3 on Nov 18 2026, source https://v2.tauri.app/release/wry/all-versions/ read 25 Nov 2026, so pin that line and do not float to latest. Second, the native composer overlay. Layout sync, focus, IME marked text and chip attachment are easy to get subtly wrong, and a bug there blocks typing all day. Notice it by the slice 3 IME tests and by dogfooding the Rust frontend for one full day before making it default. Third, virtual list and patch batching. A wrong scroll anchor or a cache key that does not include template version will show stale HTML or jump the view during streaming. Notice it by the 5,000 row snapshot and scroll stability tests in slice 2, with a hard fail if scroll position moves more than 2 px during a streaming patch while scrolled up. Fourth, typed state versus provider drift. Claude or Codex can add a field that the Rust enum rejects, or change an event shape. Notice it by the Raw passthrough variant and by a conformance fixture that includes a recent real transcript, updated weekly during the move. Fifth, fd passing for swap. A bug there loses an agent child. Notice it by never using live takeover until cold takeover is proven, and by a stop rule that disables live swap on the first adopt failure.
